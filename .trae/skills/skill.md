## 6. Git 规范 
		
		### 6.1 分支规范 
		
		- `main` 分支为主分支，用于发布稳定版本，除项目负责人外不允许直接提交到该分支 
		- `dev` 分支为开发分支，用于合并各个功能分支，包含最新开发完成的功能模块，可能存在少量 bug，但不应影响项目整体运行，除项目负责人外不允许直接提交到该分支 
		- 到达项目里程碑时，经评审人、负责人测试通过后，将 `dev` 分支以 `squash` 的方式合并到 `main` 分支，打上对应版本号的 tag 
		- **如项目中不存在 `dev` 分支，则 `main` 分支即视为 `dev` 开发分支，下同** 
		- `feat/[负责人]/[模块名]` 分支为功能分支 (如 `feat/zhangsan/dashboard`)，需基于 `dev` 分支创建，用于开发某个功能模块 
		- 开发过程中，如果本分支需要用到其他分支新提交的代码，例如 `dev` 分支，可以进行 `git merge dev`，将最新的 `dev` 分支合并进来 
		- 开发完成后，分支负责人首先应在该分支上执行 `git merge dev` 合并最新代码，如有冲突，应解决冲突后再提交 
		- 冲突解决后，由分支负责人在仓库中点击 `请求评审`，创建一个目标为 `dev` 分支的 Pull Request 
		- 评审人进行代码审查和测试，通过后，点击 `合并分支` 合并到 `dev` 分支 
		- 若评审或测试不通过，视情况决定拒绝 PR 或要求修改 (评审要求修改时，请不要创建新的分支或关闭已有 PR，直接向打开 PR 的源分支继续提交新的 Commit，修改会同步到处于 Open 状态的 PR 中) 
		- `fix/[负责人]/[模块名_缺陷名]` 分支为修复分支 (如 `fix/zhangsan/dashboard_crash`)，用于修复某个 bug，流程与功能分支类似 
		
		> [!TIP] 
		> 
		> 分支名中的负责人名可使用全拼或首字母缩写，例如 `zhangsan` 或 `zs`; 
		> 
		> 模块名或缺陷名应简洁明了，不要过长，不要使用中文; 如有必要使用多个单词，使用 `_` 分隔。 
		
		### 6.2 Commit 规范 
		
		- **提交粒度**: 每次提交应是一个逻辑上完整的改动单元，避免在一个 Commit 中混合多个不相关的修改 
		- 正确示例: 一个 Commit 完成一个完整的功能点或修复一个 bug 
		- 错误示例: 一个 Commit 中既有新功能开发，又有不相关的 bug 修复或代码格式调整 
		
		- **提交频率**: 建议小步快走，频繁提交 
		- 完成一个独立的功能模块后应及时提交 
		- 修复一个 bug 后应及时提交 
		- 避免积累大量代码后一次性提交 
		- 复杂功能或页面拆分为多个小功能点，每个小功能点单独提交，确保每个提交能够在 Commit Message 中用一句话描述清楚 
		- 例如: 先在一个提交中搭建大致功能框架，实现细节先保留 TODO 注释，后续再分多个提交完成实现细节 
		
		- **提交前检查**: 在每次提交前，应确保： 
		- 代码可以正常编译运行，没有明显的运行时错误 
		- 已执行 `bunx tsc` 和 `bun lint` 进行代码检查，没有错误 
		- 已执行 `bun format` 进行代码格式化 
		- 没有提交调试代码（如 `console.log`、临时注释等） 
		- 没有提交敏感信息（如 API Key、密码等） 
		- 没有提交不必要的文件（如 IDE 配置、临时文件等，应添加到 `.gitignore`） 
		
		- **代码审查**: 提交到远程仓库前，建议自行进行代码审查 
		- 使用 `git diff` 或 IDE 的 diff 工具查看修改内容，确保所有改动都是有意为之 
		- 检查是否有遗漏的文件或不小心删除的代码 
		
		### 6.3 Commit Message 规范 
		
		> 参考 [Conventional Commits](https://www.conventionalcommits.org/zh-hans/v1.0.0/) 规范 Commit Message 
		
		Commit Message 的主要格式如下: 
		
		``` 
		<类型>[可选 影响范围或模块]: <描述> 
		
		[可选 正文] 
		
		[可选 脚注] 
		``` 
		
		例如 `feat(api): send an email to the customer when a product is shipped` 
		
		日常的提交若没有需要特别说明的信息，可以省略正文和脚注，请参考仓库历史 Commit 记录，保持风格一致 
		
		描述和正文可使用中文或英文，类型从以下列表中选择 
		
		- `<类型>` 包括: 
		- `feat`: 新功能 
		- `fix`: 修复 bug 
		- `ui`: 仅修改了 UI 界面显示样式，不影响功能逻辑 
		- `docs`: 文档更新，例如修改 README 文件、API 文档等 
		- `style`: 代码格式、样式调整，例如调整缩进、空格、空行等 
		- `refactor`: 重构代码，例如修改代码结构、变量名、函数名等但不修改功能逻辑 
		- `perf`: 用于优化性能，例如提升代码的性能、减少内存占用等 
		- `test`: 测试用例相关，例如添加、删除、修改代码的测试用例等 
		- `build`: 构建相关，例如添加、升级依赖库，改进构建流程等 
		- `ci`: CI/CD 相关，例如修改 GitHub Actions 等工作流配置 
		- `chore`: 其他杂项 
		
		更多规范的示例请参考 [Conventional Commits](https://www.conventionalcommits.org/zh-hans/v1.0.0/)
